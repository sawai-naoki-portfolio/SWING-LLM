# 企画・要件定義書 — SWING-LLM

## 1. 企画の背景

生成 AI の多くは、海外の大企業が学習した既製のモデルを API やダウンロードで使う形で提供されています。便利な一方で、

- モデルが**何を学習し、どう作られたか**を利用者側では説明できない
- 既製モデルの**ライセンスや利用規約を引き継ぐ**ため、用途や配布に制約がかかる
- 声や画像を生成できる AI は、**本人の同意のない声の複製**や有害な画像の生成といった悪用の心配がある

という課題があります。国や企業が「自分で制御できる AI（ソブリン AI）」を求める動きや、1 台の端末で動く小さなモデル（SLM）が伸びていることも背景にあります。

一方、国内でゼロから学習している大規模モデルは大企業・研究機関によるもので、個人が同じ規模で競うことは現実的ではありません。そこで本作品では「規模」ではなく、**仕組みを一から自分で作り、説明できること**に価値を置きました。

## 2. コンセプト

> **LLM・音声・画像の 3 つの AI を、学習データの整備からモデル・学習・評価・配信まで、1 台の PC でゼロから自作する。**

| 方針 | 内容 |
|---|---|
| 完全自作 | 答えを作る頭脳（LLM・TTS・画像生成）は自作する。既製の LLM（Qwen など）は 2026 年 10 月に撤去した。外部の学習済みモデルは「学習データの安全フィルタ」「評価の物差し」と、ASR・VAD・RAG の埋め込みなどの周辺機能に限る |
| 1 台で完結 | 12GB の GPU 1 枚（RTX 5070 想定）で学習から配信まで回す。GPU が無くても CPU で動く |
| 安全を最初から | 声のクローンは本人の同意が必須、すべての音声出力に電子透かし、画像の学習データは有害判定と重複除去を通す |
| 測ってから投資する | 学習に計算資源を注ぐ前に、評価ゲート（正答率・検索の再現率・パープレキシティ・PSNR・SNR など）を整える |

## 3. 対象ユーザー

| ペルソナ | 特徴 |
|---|---|
| 開発者（自分） | 1 台の PC で学習・評価・配信を繰り返し、モデルの中身を理解しながら改良したい |
| 利用者 | ブラウザやスマホから、文章の会話・画像についての質問・読み上げ・画像生成をひとつの画面で使いたい |
| レビュアー | 作り・安全機構・品質の確かめ方を、コードと文書から追いたい |

## 4. 機能要件

### 4-1. 利用者向け（Web UI / API）

| ID | 機能 | 内容 |
|---|---|---|
| F-01 | 会話 | ストリーミングで逐次表示。会話の履歴（8 ターン）を文脈に使う |
| F-02 | 思考モード | `<think>` で考えてから答える。考えた過程を折りたたみで表示 |
| F-03 | 高品質モード | N 個の候補から PRM ヘッドの点数が最も高いものを選ぶ（Best-of-N） |
| F-04 | ツールの自動実行 | 計算・天気・文書検索を意図から先回りして実行し、結果をそのまま表示。モデル自身も `<tool_call>` でツールを呼べる |
| F-05 | 文書検索（RAG） | 手元の文書から根拠を探し、根拠が足りなければ断定しない |
| F-06 | 画像の質問 | 画像を添付・ドラッグ＆ドロップして質問する |
| F-07 | 読み上げ | 自作の TTS（未学習ならブラウザの音声）で回答を読み上げる。ストリーミングと WebSocket に対応 |
| F-08 | 声のクローン | 参照音声の声で読み上げる。話者ごとの明示同意が無ければ拒否 |
| F-09 | 音声入力 | 話した内容をテキストにする。Web UI はブラウザの音声認識、API は `/api/asr`（faster-whisper）を提供 |
| F-10 | 画像生成 | プロンプトから画像を生成する |
| F-11 | ペルソナ | JARVIS（冷静・論理的）と NAVI（くだけた口調） |
| F-12 | フィードバック | 回答に 👍 / 👎 をつけ、継続学習の材料として集める |
| F-13 | 会話の管理 | 会話はブラウザ内だけに保存。履歴の切り替え・削除 |

### 4-2. 開発者向け（学習・運用）

| ID | 機能 | 内容 |
|---|---|---|
| F-20 | パイプライン | `run.bat llm\|voice\|image\|all MODE` で、データ整備から学習・評価・E2E までを順に実行 |
| F-21 | モード | TEST（数分）/ SMOKE / PROD（数時間）/ MAX（数日）で規模を切り替える |
| F-22 | 部分実行 | ステージ単位の実行・範囲指定・スキップ・並列・失敗しても続行・ドライラン |
| F-23 | 評価ゲート | 評価ステージの結果がしきい値を下回ったら、終了コードでパイプラインを止める |
| F-24 | チェックポイント | 状態の表示・一覧・削除・退避・復元。中断しても続きから再開 |
| F-25 | 大規模コーパス | トークン数の予算（例: 40 億トークン）を指定して、複数ソースを比率どおりに混ぜたコーパスを作る |
| F-26 | 継続学習 | LoRA とリプレイバッファで、フィードバックをもとに追加学習する |

## 5. 非機能要件

| 区分 | 要件 | 実現方法 |
|---|---|---|
| セキュリティ | 他サイトや DNS リバインディングから操作されない | Host を常に検証、書き込みと WebSocket は Origin も検証、トークン認証（任意） |
| セキュリティ | 公開の設定ミスで無防備にならない | 外部に公開する待ち受けで許可ホストが無ければ起動しない（fail-closed） |
| セキュリティ | モデル経由で任意のコードを実行されない | Python 実行ツールは既定で無効。有効でも Docker またはホワイトリスト方式のサンドボックス |
| セキュリティ | 悪意ある重みファイルで乗っ取られない | 配信の読み込みは `weights_only=True` |
| プライバシー | 入力内容を残さない | ログには長さ・件数だけを記録。会話はブラウザ内だけに保存 |
| 安全 | 声を勝手に複製させない | 同意台帳での確認、すべての出力に電子透かし |
| 可用性 | 学習前・部品不足でも動く | 遅延ロード、未学習時は 503 とブラウザ側の代替、BM25・RMS・AST 方式への縮退 |
| 性能 | 1 台のマシンを守る | 同時生成 2 本、レート制限、本文 12MB・プロンプト 4,000 文字の上限、切断時の生成停止 |
| 堅牢性 | 長時間の学習を失わない | アトミックな保存、30 分ごとの保存、読めないチェックポイントでは止まる |
| 保守性 | 品質を自動で確かめる | ユニットテスト 762 件、ruff・mypy、GitHub Actions、評価ゲート |
| 移植性 | Windows の日本語パスでも動く | ログの文字コード対策、索引の保存に非 ASCII パス対応の方法を使う |

## 6. 範囲外・今後の課題

| 項目 | 理由・方針 |
|---|---|
| 製品水準の日本語対話 | 大規模な事前学習（数十億トークン）が必要。トークン予算コーパスと学習の再開の仕組みまでは用意済み |
| インターネットへの公開 | TLS 終端（リバースプロキシ）、ヘルスチェック、プロセス管理が未対応。今は手元（127.0.0.1）での利用が前提 |
| 生成画像の安全チェック | 出力の有害判定・透かし・C2PA は未実装（学習データ側の対策のみ） |
| 音声透かしの強化 | 自作の方式は切り貼り・再圧縮に弱い。安全に関わる変更のため慎重に進める |
| モバイルアプリ | Flutter で別のリポジトリで開発。この作品には含めていない（同じ API を使う） |
